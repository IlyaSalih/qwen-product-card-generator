# AI-помощник для подготовки товарных описаний

Локальный CLI-прототип, который создаёт черновики B2B-карточек контрольно-измерительных приборов через Qwen или другую модель с OpenAI-совместимым API.

Проект выполнен как тестовое задание для вакансии AI-разработчика. Он не требует базы данных, CMS, векторного хранилища или деплоя.

> **Перед отправкой:** второй товар в `examples/products.json` — явно помеченный демонстрационный вход, поскольку в PDF присутствовал только один пример. Замените его на второй товар от проверяющих. Файлы в `examples/outputs/` являются проверенными референсными примерами, а не результатом запуска вашего Qwen. Перед сдачей перегенерируйте их локально по инструкции ниже.

## Возможности

- принимает один товар или массив товаров в JSON;
- работает с локальным Qwen через Ollama, LM Studio, vLLM и аналогичные серверы;
- формирует SEO-заголовок, SEO-описание, 3–5 поисковых запросов и commercial-блок;
- сохраняет результат в JSON и удобном для копирования Markdown;
- копирует характеристики напрямую из входных данных, минуя генерацию LLM;
- явно отмечает пустые поля как `данных нет` и собирает список необходимых уточнений;
- проверяет длину заголовка и описания, количество и уникальность запросов;
- обнаруживает числовые значения, которых не было во входных данных;
- повторно обращается к модели с замечаниями валидатора;
- обрабатывает неправильный JSON, ошибки соединения, таймаут и HTTP-ошибки API;
- продолжает обработку остальных товаров, если генерация одного завершилась ошибкой.

## Как устроено решение

```text
Входной JSON
    │
    ▼
Pydantic: проверка структуры и пустых полей
    │
    ▼
Qwen: только SEO-тексты, запросы и commercial-блок
    │
    ▼
Разбор JSON + независимые валидаторы
    │
    ├── ошибка ──► замечания модели и повторная попытка
    │
    ▼
Программное копирование исходных характеристик
    │
    ▼
JSON + Markdown
```

LLM не формирует список характеристик и список отсутствующих данных. Эти части собираются детерминированно, поэтому модель не может случайно изменить значение характеристики в итоговом списке.

## Требования

- Python 3.10 или новее;
- запущенный локальный сервер с OpenAI-совместимым Chat Completions API;
- установленная instruct-модель Qwen, достаточная для генерации связного русского текста.

## Быстрый запуск с Ollama

1. Проверьте точное имя установленной модели:

   ```bash
   ollama list
   ```

2. Если сервер ещё не запущен, выполните в отдельном терминале:

   ```bash
   ollama serve
   ```

3. Создайте окружение и установите проект:

   ```bash
   python -m venv .venv
   source .venv/bin/activate
   # Windows PowerShell: .venv\Scripts\Activate.ps1
   python -m pip install -e ".[dev]"
   ```

4. Создайте локальную конфигурацию:

   ```bash
   cp .env.example .env
   # Windows: copy .env.example .env
   ```

5. В `.env` укажите имя модели из `ollama list`:

   ```dotenv
   LLM_BASE_URL=http://localhost:11434/v1
   LLM_MODEL=qwen2.5:7b
   LLM_API_KEY=ollama
   LLM_TIMEOUT=120
   LLM_MAX_ATTEMPTS=3
   ```

   `LLM_API_KEY=ollama` — техническая заглушка для локального сервера, а не секрет. Файл `.env` добавлен в `.gitignore`.

6. Проверьте входные данные без обращения к модели:

   ```bash
   product-card examples/products.json --validate-only
   ```

7. Запустите генерацию:

   ```bash
   product-card examples/products.json --output-dir outputs --print
   ```

Вместо `product-card` можно использовать `python -m product_card` с теми же аргументами.

### LM Studio и vLLM

Измените только адрес и имя модели:

```dotenv
# LM Studio, стандартный локальный порт
LLM_BASE_URL=http://localhost:1234/v1
LLM_MODEL=имя-модели-из-LM-Studio

# vLLM с --served-model-name qwen
# LLM_BASE_URL=http://localhost:8000/v1
# LLM_MODEL=qwen
```

Параметры `--base-url` и `--model` переопределяют `.env` для отдельного запуска:

```bash
product-card examples/products.json --base-url http://localhost:11434/v1 --model qwen2.5:7b
```

## Входной формат

Можно передать один объект или непустой массив объектов:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Правила:

- `name` — обязательное непустое поле;
- `manufacturer` и `description` могут отсутствовать, тогда они попадут в список уточнений;
- `specs` — объект со скалярными значениями: строками, числами или `null`;
- пустые и `null`-значения характеристик выводятся как `данных нет`;
- дополнительные поля верхнего уровня разрешены и передаются модели как часть исходного контекста.

## Результат

Для каждого товара создаются `product_01.json`, `product_01.md` и аналогичные файлы с следующими полями:

- `seo_title` — до 70 символов;
- `seo_description` — от 800 до 1200 символов с пробелами;
- `characteristics` — исходные характеристики без переписывания моделью;
- `search_queries` — 3–5 уникальных запросов;
- `commercial_block` — краткий блок для менеджера;
- `missing_data` — отсутствующие или требующие уточнения входные поля;
- служебные сведения о товаре и использованной модели.

Примеры находятся в `examples/outputs/`.

Чтобы заменить референсные примеры реальным результатом Qwen:

```bash
product-card examples/products.json --output-dir examples/outputs
```

После генерации вручную проверьте оба текста и зафиксируйте изменения в Git.

## Проверки и защита от выдуманных характеристик

1. **Разделение ответственности.** Модель создаёт только четыре текстовых поля. Характеристики и предупреждения формирует код.
2. **Строгий промпт.** Запрещены новые факты, числа, стандарты, сертификаты, условия продажи и неподтверждённые области применения.
3. **Структурная проверка.** Ответ разбирается как JSON и валидируется Pydantic-схемой.
4. **Проверка ограничений.** Отдельно контролируются длины текстов и количество поисковых запросов.
5. **Числовой контроль.** Числа нормализуются (`1,5` и `1.5`, `02` и `2`) и сравниваются с числами из исходного JSON.
6. **Исправляющая обратная связь.** При ошибке модель получает список нарушений и генерирует ответ повторно. По умолчанию доступно три попытки.

Автоматическая проверка чисел снижает риск, но не является полноценным доказательством фактологической корректности. Финальная проверка контент-менеджером обязательна.

## Тесты и качество кода

```bash
pytest
ruff check .
```

Тесты используют fake-LLM и не требуют запущенного Qwen. Покрыты:

- корректный одиночный и пакетный вход;
- повреждённый и пустой JSON;
- пустые значения и пометка `данных нет`;
- неизменность характеристик;
- нарушение лимитов и дубли запросов;
- ответ в Markdown code fence;
- неподтверждённые числовые значения;
- повторная генерация с обратной связью;
- сохранение JSON и Markdown;
- коды возврата CLI.

GitHub Actions запускает Ruff и тесты на Python 3.10 и 3.12 для push в `main` и pull request.

## Коды возврата CLI

- `0` — все товары обработаны или входной JSON успешно проверен;
- `1` — генерация хотя бы одного товара завершилась ошибкой;
- `2` — входной файл или конфигурация некорректны.

## Принятые решения

- **CLI вместо веб-интерфейса.** Задание допускает JSON на входе и не требует UI. Так проект проще запустить, проверить и поддерживать.
- **OpenAI-совместимый API.** Один адаптер работает с Ollama, LM Studio и vLLM без привязки к конкретной версии Qwen.
- **JSON как контракт.** Markdown-прослойка разрешена при разборе ответа, но лишние поля и неправильные типы отклоняются.
- **Минимум зависимостей.** OpenAI SDK, Pydantic и python-dotenv; тестовые зависимости вынесены в `dev`.
- **Никаких секретов в Git.** `.env` игнорируется, в репозитории только `.env.example`.

## Ограничения и возможные улучшения

- Проверяются новые числа, но не все семантические искажения: например, модель может стилистически неверно истолковать уже существующий факт.
- Не выполняется полноценная сверка единиц измерения, стандартов и отраслевой терминологии с внешними источниками.
- Качество текста и способность следовать JSON-контракту зависят от выбранной локальной модели.
- Для production полезно добавить схему ответа `json_schema`, если сервер её поддерживает, очередь задач, наблюдаемость, rate limiting и набор эталонных продуктовых тестов.
- Можно добавить простую веб-форму, но она не нужна для текущего MVP.
- Перед публикацией реальной карточки необходима проверка специалиста и документации производителя.

## Публикация на GitHub

Локальный репозиторий уже содержит Git-историю. Рекомендуемый вариант — **приватный репозиторий** с доступом для проверяющих.

## Готовое сопроводительное сообщение

> Реализован локальный CLI-прототип генерации карточек товаров через Qwen с OpenAI-совместимым API. Сервис принимает один или несколько JSON-объектов, возвращает JSON и Markdown, обрабатывает неполные данные и ошибки API. Для снижения риска галлюцинаций характеристики копируются программно, а текстовый ответ проходит структурную проверку, контроль ограничений и проверку новых числовых значений. Добавлены автоматические тесты, GitHub Actions, примеры и инструкция запуска. Основная сложность — получить от локальной модели устойчивый JSON и описание заданной длины без добавления неподтверждённых фактов; для этого реализованы повторные попытки с замечаниями валидатора. Ограничения и направления развития описаны в README.

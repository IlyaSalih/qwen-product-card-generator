# AI-помощник для подготовки товарных описаний

Локальный CLI-прототип для подготовки B2B-карточек контрольно-измерительных приборов. Поддерживает два независимых результата:

- **безопасную карточку** — детерминированно собирается только из входных фактов и не требует запущенной LLM;
- **черновик Qwen** — создаётся через OpenAI-совместимый API, сохраняется отдельно и требует ручной фактологической проверки.

По умолчанию включён безопасный режим: свободный текст модели не попадает в итоговую карточку автоматически. Это решение принято после реальных ручных тестов Qwen3:8b, в которых модель иногда добавляла неподтверждённые свойства даже после успешной структурной валидации.

Для работы не требуются база данных, CMS, векторное хранилище или деплой.

## Выбранные товары и источники

В `examples/products.json` находятся два реальных предложения из [XML-каталога СОЮЗ-ПРИБОР](https://www.souz-pribor.ru/yml/any/feed.xml):

1. **ПРОМА ТБ-100-О-211-120-G1/2-100-1,5**, ID предложения `371566`. Модификация выбрана из XML; описание и характеристики сверены со [страницей термометров ТБ](https://www.souz-pribor.ru/product/tb/).
2. **ОВЕН ПД100-ДИ1,6-111-0,5**, ID предложения `73410`. Модификация выбрана из XML; описание и характеристики сверены со [страницей датчиков ПД100](https://www.souz-pribor.ru/product/pd100-di-div-dv-da-111-171-181/).

XML содержит идентификаторы, названия модификаций и ссылки, но не содержит описаний и технических параметров. Поэтому входные JSON собраны из XML и публичных страниц товаров. Цена, остатки и сроки поставки не используются, чтобы не включать в примеры быстро меняющиеся коммерческие данные. Поля `source_offer_id` и `source_url` сохранены для проверки происхождения исходных сведений.

Примеры в `examples/outputs/` созданы в безопасном режиме без ручной подмены текста. Их можно воспроизвести одной командой.

## Возможности

- принимает один товар или массив товаров в JSON;
- формирует SEO-заголовок до 70 символов, SEO-описание 800–1200 символов, 3–5 поисковых запросов и commercial-блок;
- сохраняет результат в JSON и Markdown;
- копирует характеристики напрямую из входных данных, минуя генерацию LLM;
- явно отмечает пустые поля как `данных нет` и собирает список необходимых уточнений;
- в безопасном режиме не выводит назначение товара, если оно не подтверждено исходным описанием;
- отфильтровывает из безопасного результата предложения с типичными prompt-injection инструкциями;
- работает с локальным Qwen через Ollama, LM Studio, vLLM и аналогичные серверы;
- сохраняет LLM-черновик отдельно от безопасного результата;
- проверяет ответ LLM по JSON-схеме, длинам, количеству запросов, новым числам и отдельным неподтверждённым обещаниям;
- повторно обращается к модели с замечаниями валидатора и предыдущим ответом для редактирования;
- обрабатывает неправильный JSON, ошибки соединения, таймаут и HTTP-ошибки API;
- продолжает обработку остальных товаров, если LLM-генерация одного завершилась ошибкой.

## Режимы работы

| Команда | Основной результат | Обращение к Qwen | Назначение |
|---|---|---:|---|
| `--mode safe` | `generation_mode: safe` | Нет | Воспроизводимый результат только из входных данных |
| `--mode safe --save-llm-draft` | Безопасная карточка + `*_llm_draft.*` | Да | Сравнение безопасного результата с LLM-черновиком |
| `--mode llm` | `generation_mode: llm_draft` | Да | Экспериментальный свободный черновик для ручной редактуры |

Режим можно также задать переменной `GENERATION_MODE=safe` или `GENERATION_MODE=llm`. Аргумент `--mode` имеет приоритет над `.env`.

Ошибка Qwen при использовании `--save-llm-draft` выводится как предупреждение, но не отменяет уже подготовленный безопасный результат. Файл `*_llm_draft.*` нельзя считать фактологически проверенным только потому, что он прошёл автоматические валидаторы.

## Как устроено решение

```text
Входной JSON
    │
    ▼
Pydantic: проверка структуры и пустых полей
    │
    ├───────────────────────────────┐
    ▼                               ▼
SafeCardGenerator                 QwenClient (опционально)
    │                               │
    │                               ▼
    │                         JSON + валидаторы + повторные попытки
    │                               │
    │                               ▼
    │                         Отдельный LLM-черновик
    ▼
Копирование характеристик,
безопасные шаблоны, фильтр инструкций
    │
    ▼
Основные JSON + Markdown
```

LLM никогда не формирует итоговый список характеристик и список отсутствующих данных. В безопасном режиме модель также не участвует в формировании SEO-текста, запросов и commercial-блока.

## Требования

- Python 3.10 или новее;
- для безопасного режима — только Python-зависимости из `pyproject.toml`;
- для LLM-черновика — запущенный OpenAI-совместимый Chat Completions API и instruct-модель Qwen.

## Установка

```bash
python -m venv .venv
source .venv/bin/activate
# Windows PowerShell: .venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
```

Создайте локальную конфигурацию:

```bash
cp .env.example .env
# Windows: copy .env.example .env
```

Файл `.env` добавлен в `.gitignore`. `LLM_API_KEY=ollama` — техническая заглушка для локального сервера, а не секрет. Для удалённого API ключ задаётся только через окружение или локальный `.env`.

## Быстрый запуск

Проверка входных данных без обращения к модели:

```bash
product-card examples/products.json --validate-only
```

Безопасная генерация без запущенного Qwen:

```bash
product-card examples/products.json --mode safe --output-dir outputs/safe --print
```

Безопасный результат плюс отдельный черновик Qwen:

```bash
product-card examples/products.json \
  --mode safe \
  --save-llm-draft \
  --output-dir outputs/hybrid
```

Только экспериментальный черновик Qwen:

```bash
product-card examples/products.json --mode llm --output-dir outputs/llm
```

Вместо `product-card` можно использовать `python -m product_card` с теми же аргументами.

### Настройка Ollama

Проверьте точное имя модели и при необходимости запустите сервер:

```bash
ollama list
ollama serve
```

Пример `.env`:

```dotenv
LLM_BASE_URL=http://localhost:11434/v1
LLM_MODEL=qwen3:8b
LLM_API_KEY=ollama
LLM_TIMEOUT=300
LLM_MAX_ATTEMPTS=5
GENERATION_MODE=safe
```

### LM Studio и vLLM

Измените только адрес и имя модели:

```dotenv
# LM Studio, стандартный локальный порт
LLM_BASE_URL=http://localhost:1234/v1
LLM_MODEL=имя-модели-из-LM-Studio

# vLLM с --served-model-name qwen
# LLM_BASE_URL=http://localhost:8000/v1
# LLM_MODEL=qwen
```

Параметры `--base-url` и `--model` переопределяют `.env` для отдельного запуска:

```bash
product-card examples/products.json \
  --mode llm \
  --base-url http://localhost:11434/v1 \
  --model qwen3:8b
```

## Входной формат

Можно передать один объект или непустой массив объектов:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления."
}
```

Правила:

- `name` — обязательное непустое поле;
- `manufacturer` и `description` могут отсутствовать, тогда они попадут в список уточнений;
- `specs` — объект со скалярными значениями: строками, числами или `null`;
- пустые и `null`-значения характеристик выводятся как `данных нет`;
- дополнительные поля верхнего уровня разрешены и передаются модели как часть исходного контекста;
- безопасный режим считает входные поля подтверждённым источником, но не проверяет их истинность по внешней документации.

## Результат

Для каждого товара создаются `product_01.json`, `product_01.md` и аналогичные файлы со следующими полями:

- `seo_title` — до 70 символов;
- `seo_description` — от 800 до 1200 символов с пробелами;
- `characteristics` — исходные характеристики без переписывания моделью;
- `search_queries` — 3–5 уникальных запросов;
- `commercial_block` — краткий блок для менеджера;
- `missing_data` — отсутствующие или требующие уточнения входные поля;
- `generation_model` — использованная модель или `deterministic-safe-renderer`;
- `generation_mode` — `safe` или `llm_draft`;
- служебные сведения о товаре и производителе.

При `--save-llm-draft` дополнительно создаются `product_01_llm_draft.json` и `.md`. Они не перезаписывают основной безопасный результат.

Чтобы воспроизвести референсные примеры:

```bash
product-card examples/products.json --mode safe --output-dir examples/outputs
```

## Проверки и защита от выдуманных характеристик

### Безопасный режим

1. Название, производитель и характеристики берутся только из входного JSON.
2. Описание разбивается на предложения; типичные инструкции модели и рекламные команды отклоняются.
3. Commercial-блок использует только исходные предложения с явно указанным назначением или применением. Если их нет, выводится `данных нет` и запрос описания менеджером.
4. Недостающие поля не восстанавливаются по названию модификации и не заменяются вероятными значениями.
5. Общие рекомендации по проверке документации не содержат новых свойств товара.
6. Результат детерминирован: одинаковый вход даёт одинаковый выход.

### LLM-черновик

1. Строгий промпт запрещает новые факты, числа, стандарты, сертификаты, условия продажи и неподтверждённые области применения.
2. Ответ разбирается как JSON и валидируется Pydantic-схемой.
3. Отдельно контролируются длины текстов и количество поисковых запросов.
4. Числа нормализуются (`1,5` и `1.5`, `02` и `2`) и сравниваются с числами из исходного JSON.
5. Правила отклоняют отдельные неподтверждённые утверждения о надёжности, стабильности, сохранении точности и работе без модификаций.
6. При ошибке модель получает список нарушений, целевую длину и предыдущий ответ для редактирования.
7. Температура запроса установлена в `0.0` для уменьшения вариативности.

Эти проверки снижают риск, но не доказывают семантическую корректность свободного текста. Поэтому LLM-черновик изолирован от основного результата.

## Автоматические и ручные тесты

```bash
pytest
ruff check .
ruff format --check .
```

В наборе 30 автоматических тестов. Используются fake-LLM и детерминированный генератор; запущенный Qwen не нужен. Покрыты:

- корректный одиночный и пакетный вход;
- повреждённый и пустой JSON;
- пустые значения и пометка `данных нет`;
- неизменность характеристик;
- нарушение лимитов и дубли запросов;
- ответ в Markdown code fence;
- неподтверждённые числа и качественные утверждения;
- повторная генерация с обратной связью;
- оба реальных примера в безопасном режиме;
- неполный товар, prompt injection и очень длинный вход;
- отсутствие обращения к LLM в безопасном режиме;
- сохранение безопасного результата при сбое LLM-черновика;
- сохранение JSON и Markdown и коды возврата CLI.

Практические сценарии и ранее обнаруженные ошибки Qwen задокументированы в [MANUAL_TESTS.md](MANUAL_TESTS.md). GitHub Actions запускает Ruff и тесты на Python 3.10 и 3.12 для push в `main` и pull request.

## Коды возврата CLI

- `0` — все основные результаты подготовлены или входной JSON успешно проверен; сбой дополнительного LLM-черновика в гибридном режиме не меняет этот код;
- `1` — генерация хотя бы одного основного результата завершилась ошибкой;
- `2` — входной файл или конфигурация некорректны.

## Принятые решения

- **CLI вместо веб-интерфейса.** JSON-интерфейс не требует UI, поэтому проект проще запускать, проверять и поддерживать.
- **Безопасный результат по умолчанию.** Формальная валидация не обнаружила все смысловые галлюцинации в ручных тестах, поэтому свободный текст LLM не должен автоматически становиться готовой карточкой.
- **LLM остаётся частью решения.** Qwen вызывается через API и создаёт черновик, но артефакты разделены, чтобы их нельзя было случайно перепутать.
- **OpenAI-совместимый API.** Один адаптер работает с Ollama, LM Studio и vLLM без привязки к конкретной версии Qwen.
- **JSON как контракт.** Markdown-прослойка разрешена при разборе ответа, но лишние поля и неправильные типы отклоняются.
- **Минимум зависимостей.** OpenAI SDK, Pydantic и python-dotenv; тестовые зависимости вынесены в `dev`.
- **Никаких секретов в Git.** `.env` игнорируется, в репозитории только `.env.example`.

## Ограничения и возможные улучшения

- Безопасный режим менее выразителен, чем свободный маркетинговый текст: при скудных входных данных он намеренно выводит общие рекомендации и список уточнений вместо предположений.
- Фильтр injection покрывает типичные инструкции, но не является универсальным анализатором вредоносного текста. Входные данные должны поступать из проверенного источника.
- Безопасный режим не проверяет достоверность самих входных характеристик по внешним источникам.
- В LLM-режиме остаются возможны семантические искажения, которые не попадают в список числовых и качественных правил; ручная проверка обязательна.
- Не выполняется полноценная сверка единиц измерения, стандартов и отраслевой терминологии с документацией производителя.
- Для production полезно добавить `json_schema` при поддержке сервером, очередь задач, наблюдаемость, rate limiting и расширенный набор эталонных продуктовых тестов.
- Следующий полезный шаг — извлечение фактов из проверенного паспорта в типизированную схему с указанием источника каждого поля, а не усиление свободной генерации новыми запретами.
- Можно добавить простую веб-форму, но она не нужна для текущего MVP.
